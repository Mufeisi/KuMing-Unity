## 1. 结论先行

项目可以迁移到 MonoGame，但不能按“全量重写后一次切换”的方式实施。推荐采用绞杀式迁移：

1. 保持服务器协议、`Shared` 封包和游戏规则不变。
2. 先建立旧客户端的截图、输入、封包和性能基线。
3. 先实现旧资源格式与旧绘制语义兼容层。
4. 用 MonoGame 重建同一条“登录 → 选角 → 进图 → 移动 → 战斗 → 拾取 → 聊天”垂直链路。
5. PC 端逐场景替换 SlimDX/WinForms，并通过双客户端对照验收。
6. PC 达到发布候选后，再用同一核心增加 Android/iOS Host、触控 HUD 和移动资源包。

不推荐先开发完整 GUI 编辑器，也不推荐先把全部代码“整理干净”再开始渲染。第一优先级是证明旧资源、地图、人物动画、混合模式、点击命中和封包时序能够在 MonoGame 中一致运行。

在人员完整、素材与测试账号齐备的情况下：

- 5～7 人团队：PC 100% 约 7～10 个月；移动端 80% 再增加 3～5 个月。
- 3 人团队：PC 100% 约 11～16 个月；移动端 80% 再增加 5～8 个月。
- 单人全职：预计 18～30 个月，不建议同时承诺 PC 100% 和双移动平台。

以上为工程估算，不是日期承诺。第 4 周技术验证通过后必须重新估算一次。

## 2. 当前仓库事实与迁移难点

### 2.1 已确认的项目事实

| 项目 | 当前状态 | 对迁移的影响 |
| --- | --- | --- |
| 客户端目标框架 | `net8.0-windows7.0` | 当前为 Windows 专用 |
| 窗口与事件 | WinForms `Application.Idle` + `RenderForm` | 需要替换为 MonoGame `Game` 生命周期 |
| 渲染 | SlimDX Direct3D9 | 需要重建纹理、Surface、Shader、混合与设备恢复 |
| UI | 自研 `MirControl` 控件树 | 业务界面多，可先兼容行为再演进布局 |
| 图片资源 | 自定义 `.Lib`，运行时解压并上传纹理 | 是首要技术风险 |
| 文本 | `System.Drawing` / GDI 文本测量与绘制 | 移动端不可用，PC 像素还原难度高 |
| 声音 | NAudio | Windows 绑定，需要跨平台音频实现 |
| 网络 | `TcpClient` + 收发队列 + `Shared.Packet` | 可复用，但要隔离 UI 和静态时钟依赖 |
| 浏览器 | WebView2 | 移动端不能复用，需平台 Adapter 或外部浏览器 |
| 原型 | `UiPreview` 使用 MonoGame WindowsDX | 能证明 MonoGame 环境可运行，但不含真实资源和逻辑 |
| GUI 设计 | 已有 GUI Studio PRD | 应在运行时稳定后接入，不作为迁移前置条件 |

### 2.2 代码规模信号

当前 `Client` 约有 97 个 C# 文件，其中：

- `GameScene.cs` 超过 10,000 行，同时承担场景状态、UI、封包分发和大量业务行为。
- `MonsterObject.cs`、`PlayerObject.cs` 分别超过 5,000 和 4,000 行。
- `MirScenes/Dialogs` 约 36 个文件。
- `MirControls` 约 17 个文件。
- 至少 16 个客户端文件直接引用 SlimDX。
- 至少 20 个客户端文件直接引用 `System.Drawing`。
- 至少 21 个客户端文件带有 WinForms 或桌面窗口依赖。

因此，风险不在 MonoGame 的 `SpriteBatch.Draw`，而在旧平台细节已经穿透到场景、控件、资源和对象实现中。

### 2.3 当前构建基线

- `UiPreview/UiPreview.csproj`：本次检查可编译，0 警告、0 错误。
- `Client/Client.csproj`：本次使用 `--no-restore` 构建失败，缺少 `Client/obj/project.assets.json`。
- 当前目录未被 Git 识别为有效工作树。

正式开发前必须恢复可重复的旧客户端构建与版本管理；否则无法证明迁移前后的差异来自代码，而不是环境或素材。

## 3. 产品目标与“还原率”定义

### 3.1 PC 端 100% 还原

“100%”定义为目标版本范围内的可观测行为等价，不要求内部代码结构相同。

必须同时满足：

1. 同一服务器、同一账号、同一数据包能够完成旧客户端支持的全部游戏流程。
2. 所有登录、选角、游戏场景、对话框、快捷键、鼠标行为和设置项均有对应实现。
3. 同一分辨率、同一资源、同一状态下，关键黄金截图达到约定像素差阈值。
4. 人物、怪物、技能、特效、灯光、昼夜、地图遮挡和混合模式的帧序与时序一致。
5. 声音编号、循环、延迟、音量和停止规则一致。
6. 网络封包字节、顺序、超时、重连和错误处理与服务器兼容。
7. 旧资源目录可直接使用，或能通过官方迁移工具无损转换。
8. 性能、稳定性、内存和加载时间不低于约定基线。
9. 无“临时回到旧客户端才能完成”的正式功能。

以下不属于 100% 的含义：

- 必须保留 SlimDX、WinForms 或 GDI。
- 所有 GPU 的字体抗锯齿结果逐像素完全相同。
- 必须复制旧客户端的崩溃、泄漏或明显错误。

旧错误是否保留由兼容清单逐项决定；影响玩法或服务器判定的行为默认先兼容，再单独立项修复。

### 3.2 移动端 80% 还原

移动端不按“80% 文件数量”计算，使用加权功能覆盖率：

| 能力域 | 权重 | 80% 版本要求 |
| --- | ---: | --- |
| 登录、选角、进图、断线重连 | 8 | 全部必须 |
| 移动、寻路、地图切换 | 14 | 全部必须 |
| 战斗、技能、目标选择、药品 | 20 | 全部必须 |
| 角色、装备、背包、拾取 | 12 | 全部必须 |
| NPC、任务、商店、仓库 | 12 | 主流程必须 |
| 聊天、组队、行会、好友 | 9 | 常用流程必须 |
| 交易、邮件、拍卖、商城 | 8 | 至少满足一种完整经济闭环 |
| 英雄、宠物、钓鱼等扩展系统 | 7 | 按活跃玩家使用率取舍 |
| 视觉、声音、特效 | 5 | 可降低密度，不可影响判定 |
| 设置、辅助、外链与工具功能 | 5 | 保留移动端适用部分 |

首个移动版本必须达到至少 80 分，并且前四个能力域不得缺项。不能用大量低价值设置项替代核心战斗功能。

### 3.3 非目标

- 本次不修改服务器游戏规则。
- 本次不重写服务器和数据库。
- 本次不强制把所有旧资源立即转换成 XNB。
- 本次不把 GUI Studio 做成通用设计软件。
- 移动首发不承诺所有 PC 快捷键、窗口自由拖动和后台多开。
- 不在迁移过程中同时进行大规模数值、职业或玩法重做。

## 4. 总体技术路线

### 4.1 推荐路线：共享核心 + 多平台 Host

```text
┌────────────────────────────────────────────────────────────┐
│                    Crystal.Client.Core                     │
│ 状态、规则协调、场景流程、封包处理、对象动画、命令与时钟   │
└───────────────┬──────────────────────┬─────────────────────┘
                │                      │
        ┌───────▼────────┐    ┌────────▼─────────┐
        │ Render Runtime │    │   UI Runtime     │
        │ 世界/特效/灯光 │    │ 控件/布局/命中   │
        └───────┬────────┘    └────────┬─────────┘
                └──────────┬───────────┘
                           │
                 ┌─────────▼──────────┐
                 │ Asset/Audio/Input  │
                 │ Network/Platform   │
                 └───────┬───────┬────┘
                         │       │
              ┌──────────▼─┐   ┌─▼────────────────┐
              │ Windows Host│   │ Android/iOS Host│
              │ MonoGame DX │   │ MonoGame Mobile │
              └─────────────┘   └──────────────────┘
```

### 4.2 推荐解决方案结构

```text
Client.MonoGame.sln
├─ Client.Core                 # 不引用 WinForms、SlimDX、System.Drawing
├─ Client.Protocol             # 引用 Shared，封包编解码与会话
├─ Client.Assets               # Lib/Map/Sound 元数据、CPU 解码、缓存策略
├─ Client.Rendering            # 绘制命令、世界渲染、灯光、特效
├─ Client.Ui                   # MirControl 兼容运行时与后续新 UI Runtime
├─ Client.Platform             # 平台能力接口和通用实现
├─ Client.Windows              # MonoGame WindowsDX Host
├─ Client.Android              # Android Host
├─ Client.iOS                  # iOS/iPadOS Host
├─ Client.AssetCompiler        # 可选的资源预处理和移动资源包
├─ Client.Replay               # 封包/输入录制与确定性回放
├─ Client.Tests.Unit
├─ Client.Tests.Integration
└─ Client.Tests.Visual
```

项目初期不要求一次创建所有项目。第 1 阶段只创建 `Core`、`Assets`、`Rendering`、`Windows` 和测试项目。

### 4.3 深 Module 与关键 seam

#### GameHost Module

小 Interface：

```csharp
void Initialize(GameBootOptions options);
void Update(GameTimeStep time, InputFrame input);
void Draw(RenderFrame frame);
void Shutdown();
```

其内部隐藏窗口、生命周期、异常恢复、挂起、恢复和平台事件。

#### AssetRuntime Module

小 Interface：

```csharp
SpriteFrame GetSprite(LibraryId library, int index);
MapData GetMap(MapId id);
AudioClip GetAudio(SoundId id);
void Trim(AssetBudget budget);
```

实现内部隐藏 `.Lib` 索引、GZip 解压、颜色格式、Mask、纹理页、异步读取、缓存和释放。

需要两个 Adapter，因而 seam 是真实的：

- PC 兼容 Adapter：直接读取旧 `.Lib` 与目录。
- 发布 Adapter：读取预编译资源包，供移动端和后续 PC 使用。

#### InputRouter Module

统一输出游戏动作，不把设备按键传进业务：

```csharp
InputFrame Poll();
```

Adapter：

- 键盘鼠标 Adapter。
- 触控 Adapter。
- 手柄 Adapter。
- 回放 Adapter。

业务只认识 `MoveVector`、`PrimaryAction`、`SelectTarget`、`UseSkill(slot)`、`OpenPanel(id)` 等动作。

#### NetworkSession Module

保留 `Shared.Packet`，但把 `CMain.Time`、`MirScene.ActiveScene` 和 UI 提示移出网络实现。

```csharp
ConnectionState State { get; }
void Connect(Endpoint endpoint);
void Enqueue(Packet packet);
NetworkBatch Pump(TimePoint now);
void Disconnect(DisconnectReason reason);
```

生产使用 TCP Adapter，测试和回放使用内存 Adapter。

#### RenderRuntime Module

迁移期保留一套最小“旧绘制语义”Interface，包括：

- Sprite 绘制、区域绘制、偏移、颜色和透明度。
- Normal、Additive、Magic、Grayscale 混合。
- RenderTarget、灯光合成、裁剪和线条。
- 像素可见性查询。

SlimDX Adapter 和 MonoGame Adapter 在迁移期并存。PC 切换完成后删除 SlimDX Adapter，不把临时兼容层永久扩展成大型公共接口。

### 4.4 明确禁止的路线

- 禁止在旧 `DXManager` 内部直接散布 MonoGame 类型，造成半 SlimDX 半 MonoGame。
- 禁止让业务对象直接创建 `Texture2D`、`SoundEffect` 或平台窗口。
- 禁止移动端复制一份独立游戏逻辑。
- 禁止用条件编译在数百个文件中到处写 `#if ANDROID`。
- 禁止先批量替换 `Point/Color/Rectangle` 后再处理语义差异。
- 禁止在没有黄金截图和回放的情况下声称“已经 100% 还原”。

## 5. 资源与渲染迁移设计

### 5.1 旧 `.Lib` 资源

首轮采用“兼容读取”，而不是立刻改资源生产链：

1. 把文件索引、FrameSet、图片元数据解析移入纯 .NET `Client.Assets`。
2. 解压结果统一为 CPU 端 `Rgba32Buffer`，不依赖 `Bitmap`。
3. 记录 Width、Height、Offset、Shadow、Mask、DataLength 和可见像素信息。
4. GPU 上传只允许发生在 MonoGame 图形线程。
5. PC 可直接读取旧 `.Lib`；移动包由 `AssetCompiler` 转换为纹理页与元数据。
6. 为每个测试 `.Lib` 计算输入哈希、帧数、尺寸、偏移和像素哈希。

验收样本至少包含：

- 人物站立、走、跑、攻击、受击、死亡。
- 武器、衣服、头发和叠加效果。
- 普通怪物、大体积怪物、NPC。
- UI 图片、物品、技能图标、字体或数字。
- 带 Shadow、Mask、透明边缘和空帧的资源。

### 5.2 像素格式与混合模式

必须做独立混合模式实验页，不允许凭目测在真实战斗中调：

| 旧语义 | MonoGame 候选实现 | 验收方式 |
| --- | --- | --- |
| AlphaBlend | 自定义或内置 Alpha BlendState | 颜色与边缘差异图 |
| Additive/Blend | 自定义 BlendState | 火焰、技能、光效样本 |
| Magic | Effect + BlendState | 与旧 shader 输出对照 |
| Grayscale | Effect | 灰度权重和透明度对照 |
| Tint/Opacity | SpriteBatch color 乘法 | 16 组颜色测试矩阵 |
| Mask/Shadow | 双纹理或预合并纹理页 | 人物/怪物阴影截图 |

必须确认旧图片是否使用预乘 Alpha。MonoGame `SpriteBatch` 默认行为与源数据不匹配时，会产生黑边或颜色偏暗。

### 5.3 地图渲染

地图按层处理：

1. 地表 tile。
2. 低层对象。
3. 实体与动态对象。
4. 高层遮挡。
5. 特效、伤害数字、名称和 UI。
6. Light RenderTarget 与最终合成。

优化前先保持旧排序规则。只有黄金截图一致后，才能合并批次或改变遍历结构。

### 5.4 文本

PC 100% 还原的文本策略分两段：

- 兼容阶段：固定字体文件、字号、DPI、Hinting 和测量规则，建立文本截图基线。
- 跨平台阶段：使用离线字形图集或 SDF/MSDF 字体，保留旧布局所需的度量兼容表。

不允许移动端调用 `System.Drawing`。所有运行时文本测量必须来自同一字体度量数据。

### 5.5 Shader

旧 `.ps` Shader 不直接作为跨平台交付物。需要：

1. 列出 Normal、Grayscale、Magic 和灯光合成的输入/输出语义。
2. 先为 WindowsDX 编写 MonoGame Effect。
3. 再通过 Content Pipeline 为移动目标编译。
4. 每个 Effect 建立固定输入纹理与输出哈希测试。

## 6. UI 迁移路线

### 6.1 两阶段 UI 策略

#### 第一阶段：MirControl 行为兼容

目标是尽快完成 PC 100%：

- 保留现有控件树、事件和绝对坐标语义。
- 把 WinForms `MouseEventArgs`、`KeyEventArgs` 换成平台无关输入事件。
- 把 GDI 文本和 SlimDX 纹理替换成 UI RenderRuntime。
- 保留界面类和封包交互，逐个解除 `GameScene` 静态引用。

#### 第二阶段：新 UiRuntime

当至少三个真实窗口完成兼容后，再按 `monogame-gui-studio-prd.md` 建立布局、Theme、热重载和 GUI Studio。

这两阶段不同时重写同一个窗口。每个窗口应处于以下一个状态：

- Legacy：旧客户端使用。
- Compatible：MonoGame 中由 MirControl 兼容运行时驱动。
- Native：新 UiRuntime 驱动。
- Removed：旧实现已删除。

### 6.2 PC UI 迁移顺序

1. 登录与服务器选择。
2. 角色选择。
3. 游戏主 HUD、聊天和提示。
4. 背包、装备与物品 Tooltip。
5. NPC 对话、商店和仓库。
6. 技能、魔法与快捷栏。
7. 任务与地图。
8. 组队、好友、行会。
9. 交易、邮件、拍卖和商城。
10. 英雄、宠物、钓鱼等扩展窗口。
11. 设置、帮助、外链和边缘窗口。

### 6.3 移动 UI

移动端不是把 PC UI 等比缩小。必须增加：

- 左侧虚拟摇杆或点地移动模式。
- 右侧攻击、技能、药品和拾取区。
- 目标锁定与目标切换。
- 长按、双击、拖拽、拆分数量的触控规则。
- 安全区、刘海、圆角和系统手势边缘处理。
- 软键盘输入、聊天频道和焦点恢复。
- 触控目标最小尺寸与可达性。
- 战斗 HUD 与管理窗口互斥或折叠策略。

世界坐标和 UI 坐标必须经过同一 Viewport 变换及逆变换，禁止在控件内自行换算物理像素。

## 7. 音频、网络与平台能力

### 7.1 音频

NAudio 仅保留在旧客户端。新客户端建立 AudioRuntime：

- `PlayOneShot(soundId, volume, pan)`
- `PlayLoop(soundId, channel)`
- `Stop(channel)`
- `PlayMusic(musicId, loop)`
- `SetBusVolume(bus, volume)`

首选将 WAV/MP3 在构建期转为平台适合的格式。移动端不应在战斗中首次解码大型音频。

验收必须覆盖旧 `SoundList` 编号规则、延迟播放、循环停止、音乐切换、静音和切到后台。

### 7.2 网络

第一版不改协议：

- 继续引用 `Shared`。
- 保持 `Packet.GetPacketBytes()` 和 `Packet.ReceivePacket()` 行为。
- 网络线程只产出不可变 Packet 批次。
- 所有游戏状态修改发生在 Update 线程。
- 每帧设置封包处理数量或时间预算，防止登录/传送时卡帧。
- 增加封包录制、脱敏和离线回放。

### 7.3 平台能力

通过 PlatformRuntime 处理：

- 用户数据目录与只读资源目录。
- 打开 URL。
- 剪贴板。
- 软键盘/IME。
- 屏幕方向、安全区、DPI。
- 挂起、恢复和后台音频。
- 日志、崩溃报告和设备信息。
- Android/iOS 权限与商店生命周期。

WebView2 页面在移动端默认改为系统浏览器；只有确有登录态或支付回调需要时才建立原生 WebView Adapter。

## 10. 测试与 100% 证明方法

### 10.1 四层验证

1. **数据验证**：资源元数据、封包字节、状态哈希。
2. **行为验证**：输入回放后的角色位置、对象状态、窗口状态。
3. **视觉验证**：黄金截图、动画关键帧和差异热力图。
4. **真人验证**：测试清单、长时间游玩和灰度反馈。

### 10.2 黄金截图

每个场景至少覆盖：

- 1024×768 旧基准分辨率。
- 1280×720。
- 1600×900。
- 1920×1080。
- 窗口、全屏。
- 中文、英文。
- 正常、Hover、Pressed、Disabled、Dragging。
- 白天、夜晚和典型灯光。

验收规则：

- 世界 Sprite 和 UI 纹理使用严格像素阈值。
- 字体允许独立阈值或遮罩区域。
- 所有差异必须归类为 Bug、已接受差异或基线错误。
- 不允许仅用“肉眼差不多”关闭差异。

### 10.3 封包与输入回放

- Packet trace 包含相对时间、方向、类型、长度和脱敏载荷。
- 输入记录包含逻辑坐标、动作、按下/释放、滚轮、文本和时间。
- 回放使用固定时钟和固定随机种子。
- 每 N 帧输出核心状态哈希。
- 旧客户端无法确定性运行时，以服务器结果和最终状态为准。

### 10.4 缺陷等级

| 等级 | 定义 | 发布规则 |
| --- | --- | --- |
| P0 | 崩溃、丢物、封号风险、无法登录/进图 | 立即停止发布 |
| P1 | 核心战斗/交易/任务阻断，重大视觉错位 | RC 前清零 |
| P2 | 可绕过的功能或明显视觉差异 | 发布前按清单关闭或接受 |
| P3 | 轻微表现、文案和边缘设备问题 | 可进入后续版本 |

## 11. 性能、稳定性和包体指标

第 0 阶段先采集旧客户端实际数据；下列是首版目标预算。

### 11.1 PC

目标设备档位：

- 最低：4 核 CPU、8 GB RAM、集成或入门独显、1080p。
- 推荐：6 核 CPU、16 GB RAM、中端独显、1080p/1440p。

预算：

| 指标 | 目标 |
| --- | --- |
| 1080p 代表战斗场景 | 60 FPS，P95 帧时间 ≤ 16.6 ms |
| Update CPU | P95 ≤ 4 ms |
| Draw 提交 CPU | P95 ≤ 6 ms |
| GPU | P95 ≤ 10 ms |
| 1% Low | ≥ 50 FPS |
| 战斗稳定内存 | 无持续线性增长 |
| 进图时间 | 不慢于旧客户端基线，最终目标 ≤ 3 秒 |
| 连续运行 | 72 小时无崩溃、无不可恢复设备错误 |

如果提供 100/144 FPS 选项，必须先保证游戏逻辑不再依赖渲染 FPS。

### 11.2 移动

设备分三级：

- L：最低支持设备。
- M：主流设备。
- H：高端设备。

预算：

| 指标 | L | M/H |
| --- | ---: | ---: |
| 目标 FPS | 稳定 30 | 60，可降为 30 |
| 1% Low | ≥ 24 | ≥ 45 |
| 游戏内存 | ≤ 700 MB | ≤ 1,000 MB |
| 冷启动到登录 | ≤ 8 秒 | ≤ 5 秒 |
| 进图 | ≤ 5 秒 | ≤ 3 秒 |
| 30 分钟压力测试 | 无崩溃，无持续内存增长 | 同左 |

移动端必须支持动态降级：内部渲染分辨率、粒子密度、阴影/灯光质量、远处对象更新频率和纹理等级。

## 12. 优化方向与执行顺序

优化必须按以下顺序，禁止在无数据时先做对象池和“大重构”。

### 优先级 1：可观测性

- Update、Draw、GPU、GC、网络、资源加载分区计时。
- 当前 Sprite 数、批次切换、纹理切换和 RenderTarget 次数。
- 活跃对象、控件、粒子和声音数量。
- CPU/GPU 资源占用与缓存命中率。

### 优先级 2：减少无效工作

- 地图可见区域裁剪。
- 屏幕外对象降低更新频率。
- 不可见 UI 不布局、不命中、不绘制。
- 长列表虚拟化。
- 网络每帧处理预算。

### 优先级 3：批次与状态

- 按层、纹理页、BlendState 和 Scissor 合批。
- 降低 `SpriteBatch.Begin/End` 次数。
- UI 小图和常用 Sprite 建纹理页。
- 灯光只在需要时重绘。

不能为了合批破坏旧遮挡顺序。排序一致性优先于 Draw Call 数量。

### 优先级 4：资源与加载

- 后台读取与解压，主线程 GPU 提交。
- 最近使用缓存和显存预算。
- 地图邻区预取。
- 移动端预编译纹理和音频。
- 按场景/职业/地图拆包。

### 优先级 5：GC 与数据结构

- 去除每帧 LINQ、字符串拼接和短命 List。
- 复用 RenderCommand 缓冲区。
- 粒子、伤害数字和临时效果使用有上限池。
- 热路径使用 struct/span 前先由 Profile 证明收益。

### 优先级 6：移动专项

- 内部低分辨率 RenderTarget + UI 原生分辨率合成。
- 粒子数量与灯光分辨率分级。
- 纹理 ASTC/ETC2 等平台格式评估。
- 后台、温控和电量策略。
- 触控采样与网络发送限频。

- 登录/连接、移动、战斗、角色与背包无缺项。
- Android/iOS 都完成真实设备验证。
- 安全区、软键盘、挂起恢复、来电/切后台通过。
- L/M/H 设备性能指标通过。
- 商店发布、资源更新和回滚流程可用。

## 20. 最终决策

本项目建议立项，但立项不是立即全面重写。正确的第一笔投入是 4～6 周技术验证：

1. 恢复旧客户端构建和基线。
2. 证明真实 `.Lib` 可以无损解码。
3. 证明地图、人物和关键混合模式可以在 MonoGame 中还原。
4. 证明旧协议可直接接入。
5. 产出第一张自动差异图和第一条可回放链路。

只有这五项通过，才批准后续 PC 全功能迁移预算。PC G4 通过后可以低成本预研移动端；PC G6 前不建议让大部分团队转向移动功能。
